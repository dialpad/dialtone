## Dialtone 10 at a glance

1. New theming system
1. Color refactoring
1. Typography updates
1. New layout and spacing system
1. A visual refresh across most components
1. A variety of new components
1. API updates for improved UI composition
1. Redesigned, full-responsive documentation site.

### Key Takeaways

Start with three parts of the system:

1. **The Primitive Triad:** [DtBox](/components/box.md), [DtStack](/components/stack.md), and [DtText](/components/text.md), and the shift from composing utility classes to declaring intent through props.
1. **Layout and Spacing system**: a breaking change and is built on two numbers you can do simple math with.
1. **The Mode Directive**. Using [Mode](/components/mode.md) replaces affected inverted variants and token overrides with one Vue directive attribute.

Make note of the rest and look it up when you need them, for which we encourage you to make use of the [Dialtone CLI](/cli.md) and [Dialtone MCP Server](/guides/mcp-server/).

## The Primitive Triad

The primitive triad is the main mental-model change in Dialtone 10.

</dt-box>

Basic composition previously meant assembling utility classes for background, border, spacing, type, and color. That gets harder to review as the set grows, and a coding assistant can produce plausible class names that do not exist.

Dialtone 10 moves that intent into components and props. Props with enumerated values are discoverable and validated; unsupported values warn during development instead of failing silently. Utilities remain available when a component prop does not cover the case.

Three primitives carry most of this. DtStack has been in Dialtone for a while; DtBox and DtText complete the set.

**DtBox is the container.** Surface, border, radius, shadow, padding, and size are props.

## Layout and Spacing

More than merely changing the names from `size` and `space` to `layout` and `spacing`, the system the fits a pattern that both you or an LLM can reason through.

<dt-box surface="moderate" border-width="100" border-color="subtle" border-radius="400" padding="300" min-block-size="300" class="d-my-300 d-d-flex d-ai-center d-jc-center">
  <dt-text as="p" align="center" variant="body-sm" tone="muted">[visual]</dt-text>
  <!-- [Visual: a three-row table or graphic showing the same value, 16px padding and 128px width, expressed as a token, a utility class, and a DtBox prop, with the multiplication shown. Deck slides 35 through 37.] -->
</dt-box>

The old `--dt-size-*` and `--dt-space-*` tokens were ordinal. `--dt-space-500` was `16px` and `--dt-size-800` was `128px` because the numbers identified positions in a list, and not a value you could figure out.

The new `layout` and `spacing` tokens each have a base that makes it straightforward to calculate the value of any stop.

| Token family     | Question it answers                            | Base   | Examples                                                  |
| ---------------- | ---------------------------------------------- | ------ | --------------------------------------------------------- |
| `--dt-spacing-*` | How much air? Padding, margin, gap, inset      | `8px`  | `spacing-100` = 8, `spacing-200` = 16, `spacing-300` = 24 |
| `--dt-layout-*`  | How big? Width, height, min and max dimensions | `64px` | `layout-100` = 64, `layout-200` = 128, `layout-300` = 192 |

The stop number is a **multiplier** of the base.

- `spacing-200` is 16 because 8 × 2.
- `layout-200` is 128 because 64 × 2.
- `layout-50` is 32 and `layout-75` is 48 for the same reason.

Between 0 and 200 both families provide quarter stops (25, 50, 75, 125, 150, 175); above 200 they provide half stops, so there is always a value halfway between two hundreds and you can predict where a stop you have not used will land.

<div class="d-d-grid d-g-200 d-g-cols1 md:d-g-cols2">
<div>

**Before**

```css
.thing {
  padding: var(
    --dt-space-500
  ); /* 16px, because that is where it landed in the ordinal scale */
  inline-size: var(--dt-size-800); /* 128px, likewise */
}
```

</div>
<div>

**Dialtone 10**

```css
.thing {
  padding: var(--dt-spacing-200); /* 16px, because 8 × 2 */
  inline-size: var(--dt-layout-200); /* 128px, because 64 × 2 */
}
```

</div>
</div>

The same numbers run through tokens, utilities, and props:

```vue
<!-- before -->
<div class="d-p16 d-w128"></div>
```

The [layout and spacing tokens guide](/guides/migration/layout-and-spacing-tokens/) has the full old-to-new mapping, including the handful of old stops whose nearest new value differs by a few pixels, and the migration helper rewrites the token references.

## The Mode Directive

Some regions need a different mode from their surroundings: a call bar, a hovercard over a light page, or a calling experience that stays dark. These regions previously depended on component variants, inverted tokens, or local overrides.

<dt-box surface="moderate" border-width="100" border-color="subtle" border-radius="400" padding="300" min-block-size="500" class="d-my-300 d-d-flex d-ai-center d-jc-center">
  <dt-text as="p" align="center" variant="body-sm" tone="muted">[visual]</dt-text>
  <!-- [Visual: the call bar with `v-dt-mode` on its container and nothing else, then a dark hovercard over the light app, then the always-dark call panel beside light content. Deck slides 12 through 15. Sanitize the product surfaces as needed.] -->
</dt-box>

Use the [Mode Directive](/components/mode.md) via `v-dt-mode` attribute on any element. It sets the mode for that element and everything inside it.

```vue
<dt-box v-dt-mode:invert>
  <!-- opposite of the parent -->
</dt-box>

<dt-box v-dt-mode:dark>...
  <!-- always dark -->
</dt-box>

<dt-box v-dt-mode:light>
  <!-- always light -->
</dt-box>
```

<dt-box surface="moderate" border-width="100" border-color="subtle" border-radius="400" padding="300" min-block-size="300" class="d-my-300 d-d-flex d-ai-center d-jc-center">
  <dt-text as="p" align="center" variant="body-sm" tone="muted">[visual]</dt-text>
  <!-- [Visual: three side-by-side panels, inverted, dark, light, each with a primary button, muted text, a critical action, and a link, under a page-level light/dark toggle. Deck slides 10 and 11. Inline demo candidate.] -->
</dt-box>

Because it is scoped to the element, the directive can nest. A dark call panel can contain a light popover with a dark tooltip. Affected component-level `inverted` props are deprecated in its favor. [DtModeIsland](/components/mode-island.md) provides the same behavior when adding a directive to an existing wrapper is not practical.

## Theming

Theming has four dimensions. The previous theme API coupled brand, mode, and contrast in one selection. Dialtone 10 separates them, while the new material dimensions adds control over the neutral palette. The base theme loads once; each choice applies select overrides through a `data-dt-*` attribute or the runtime API.

<dt-box surface="moderate" border-width="100" border-color="subtle" border-radius="400" padding="300" min-block-size="500" class="d-my-300 d-d-flex d-ai-center d-jc-center">
  <dt-text as="p" align="center" variant="body-sm" tone="muted">[visual]</dt-text>
  <!-- [Visual: the Dialpad Appearance panel switching brand theme, then mode, then high contrast, then material, one short muted video or four stills. Deck slides 05 through 09 are the source; sanitize the experimental theme names and anything internal-only.] -->
</dt-box>

| Dimension | What it controls                                                                          | Values                                                                 |
| --------- | ----------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Brand     | Product wrapper colors such as the top bar and navigation                                 | `default` (`dp` or `tmo`), plus a variety of named themes              |
| Mode      | Light or dark, including nested regions that differ from their parent                     | `light`, `dark`                                                        |
| Contrast  | Stronger foreground and borders.                                                          | `default`, `high`                                                      |
| Material  | The neutral palette: i.e. the black ramp foreground, surface, and border tokens reference | `sandstone` (default), `steel`, `graphite`, `iron`, `amethyst`, `jade` |

Brand is deliberately narrow, theming the product wrapper while leaving content surfaces alone. Material controls the neutral palette (aka the `black` ramp). Most black-based foreground, surface, and border tokens derive from the black ramp, so changing that ramp shifts the product's overall tone without changing each component token. The default material, Sandstone, is warmer than pure gray. Most brand themes assign a hue-aligned material automatically.

The runtime API follows the dimensions: `initDialtoneTheme()`, `setMode()`, `setBrand()`, `setContrast()`, and `setMaterial()`. The old `setTheme()` function and `data-dt-theme` attribute are deprecated. The [theme-to-mode migration guide](/guides/migration/theme-to-mode/) rewrites the calls and flags nested regions that may need a Mode Directive.

## Color

### The ramps, and their numbers

The base color ramps and their numbering were rebuilt. The original scale ran 100 through 600. Additional shades filled the gaps with numbers such as 350, 425, 450, 475, and 550. Different hues ended up with different stops, and the number said little about where a color sat in its ramp.

<dt-box surface="moderate" border-width="100" border-color="subtle" border-radius="400" padding="300" min-block-size="500" class="d-my-300 d-d-flex d-ai-center d-jc-center">
  <dt-text as="p" align="center" variant="body-sm" tone="muted">[visual]</dt-text>
  <!-- [Visual: the eleven base ramps before and after, then the same ramps with the old irregular stop numbers highlighted and the new normalized numbers. Deck slides 16 through 19 are the source, as a static pair or a two-step reveal.] -->
</dt-box>

Each ramp now has the same twelve stops: 50, 100, 200, 300, 400, 500, 600, 700, 800, 900, 950, 1000. The same number identifies the same relative position in each ramp, and adjacent stops are visibly distinct. Product colors were retuned where needed; blues, for example, moved away from purple while brand-only hues changed less.

The [color stops migration](/guides/migration/color-stops/) maps old stops to their new positions, and the [migration helper](/guides/migration/) moves eligible base-color references to semantic tokens. Foreground, surface, and border tokens remain the intended interface; direct use of a base ramp should be the exception.

### HSL to OKLCH

Dialtone colors are now defined in OKLCH instead of HSL. Two HSL colors at the same lightness can appear different in brightness depending on hue, so ramps built by stepping lightness can drift in perceived contrast and saturation.

<dt-box surface="moderate" border-width="100" border-color="subtle" border-radius="400" padding="300" min-block-size="500" class="d-my-300 d-d-flex d-ai-center d-jc-center">
  <dt-text as="p" align="center" variant="body-sm" tone="muted">[visual]</dt-text>
  <!-- [Visual: one ramp with its L, C, and H curves plotted across the twelve stops. Deck slide 22.] -->
</dt-box>

OKLCH separates lightness, chroma, and hue in a model that tracks perception more closely. Dialtone ramps use regular lightness steps, build chroma toward the middle, then taper it toward the dark end. Hue stays within a narrow range with small adjustments between stops. That gives the ramps a more consistent structure across colors.

The second reason is plumbing. Under HSL, opacity support required separate hue, saturation, lightness, alpha, and composite variables for each color, then reassembly at the point of use:

<div class="d-d-grid d-g-200 d-g-cols1 md:d-g-cols2">
<div>

**Before**

```css
--dt-color-foreground-tertiary-h: 214;
--dt-color-foreground-tertiary-s: 10%;
--dt-color-foreground-tertiary-l: 46%;
--dt-color-foreground-tertiary-hsl: var(--dt-color-foreground-tertiary-h)
  var(--dt-color-foreground-tertiary-s) var(--dt-color-foreground-tertiary-l);

color: hsla(var(--dt-color-foreground-tertiary-hsl) / var(--fco, 1));
```

</div>
<div>

**Dialtone 10**

```css
--dt-color-foreground-tertiary: oklch(...);

color: oklch(from var(--dt-color-foreground-tertiary) l c h / var(--fco, 1));
```

</div>
</div>

Relative color syntax makes the breakouts unnecessary. One token, and opacity is applied at the point of use.

The rebuild removed about 3,200 custom-property declarations from the theme CSS, reducing its minified size by 31.1% and its gzip size by 27.7%. Opacity utilities such as `d-fco*` keep working. The [HSL to OKLCH guide](/guides/migration/hsl-to-oklch/) removes remaining channel-variable references from product code.

## Typography

The default body size moves from 15px to 16px. This is one of the most visible changes because body text is everywhere.

<dt-box surface="moderate" border-width="100" border-color="subtle" border-radius="400" padding="300" min-block-size="500" class="d-my-300 d-d-flex d-ai-center d-jc-center">
  <dt-text as="p" align="center" variant="body-sm" tone="muted">[visual]</dt-text>
  <!-- [Visual: the old five-size specimen beside the new eleven-size specimen, same sample sentence. Deck slide 25.] -->
</dt-box>

The scale itself grew from five sizes to eleven. The old scale had 12, 15, 19, 27, and 38 with nothing between; the new one runs 10, 11, 12, 13, 14, 16, 18, 20, 24, 28, 32. The gaps are small enough that hierarchy no longer requires a jump of two sizes, and the largest headline is now 32px rather than 38.

DtText exposes semantic variants such as `headline-lg`, `body-md`, and `label-sm`; these are the intended way to set styled type in product. Raw size overrides remain available for exceptions. The typography utility classes (`d-headline--*`, `d-body--*`, `d-label--*`, `d-fw-*`, `d-fc-*`, `d-truncate`) are deprecated, and the [typography migration](/guides/migration/typography/) converts statically detectable uses to DtText props.

## Logical naming

Dialtone no longer says left or right. It says start and end, because writing direction is not something a design system should assume.

<dt-box surface="moderate" border-width="100" border-color="subtle" border-radius="400" padding="300" min-block-size="300" class="d-my-300 d-d-flex d-ai-center d-jc-center">
  <dt-text as="p" align="center" variant="body-sm" tone="muted">[visual]</dt-text>
  <!-- [Visual: the three-column before/after for props, utilities, and custom CSS. Deck slide 34.] -->
</dt-box>

The vocabulary is CSS's own: `inline` is the reading axis (left and right in English), `block` is the other one (top and bottom). It applies at every level:

|            | Before                          | Dialtone 10                                   |
| ---------- | ------------------------------- | --------------------------------------------- |
| Props      | `padding-left`, `align="right"` | `padding-inline-start`, `align="end"`         |
| Utilities  | `d-pl8`                         | `d-pis-100`                                   |
| Custom CSS | `padding-left: ...`             | `padding-inline-start: var(--dt-spacing-200)` |
| Slots      | `#left`, `#right`               | `#start`, `#end`                              |

The migration tooling covers many statically detectable cases. DtBox also makes the naming explicit through logical padding and size props. The [logical naming guide](/guides/migration/logical-naming/) covers props, slots, events, utilities, and custom CSS; the [border-radius guide](/guides/migration/border-radius/) covers radius utilities, which moved to logical names and numeric stops at the same time.

## Component APIs

### One vocabulary

Component APIs had accumulated inconsistencies. Some components said `danger`, others `critical`. Some overlays opened with `show`, others with `open`. Boolean props were often phrased in the negative (`hideX`), so enabling a feature meant setting something to false. Size props took t-shirt letters that had no relationship to the token scale.

Dialtone 10 standardizes these APIs on the affected components:

| Before                                        | Dialtone 10                                     |
| --------------------------------------------- | ----------------------------------------------- |
| `size="md"`                                   | `size="300"` (the common 100 through 500 scale) |
| `v-model:show`, `:show`                       | `v-model:open`, `:open`                         |
| `kind="danger"`, `type="success"`             | `kind="critical"`, `type="positive"`            |
| `hideThing`                                   | `showThing`                                     |
| `title="..."` on overlays                     | `header-text="..."`                             |
| `@input`, `@change` on form components        | `@update:model-value`                           |
| `rootClass`, `wrapperClass`, `containerClass` | removed; use slot class props                   |
| `<a class="d-btn d-btn--primary" href="...">` | `<dt-button href="...">`                        |
| `<router-link class="d-link" :to="...">`      | `<dt-link :to="...">`                           |

Navigation now belongs in the components instead of borrowed classes. DtButton with `href` renders an anchor; DtLink with `to` renders a router link. This replaces workarounds such as styling an anchor with button classes.

Numeric sizes use the same vocabulary as the token system and extend without inventing a name between `sm` and `md`. `100` through `500` is the common component range, though some components have broader or specialized options. T-shirt sizes remain as deprecated aliases where documented.

These changes span several guides, each with tooling: [component props](/guides/migration/component-props/) for the rename pass, [component sizes](/guides/migration/component-sizes/) for numeric sizes, [success to positive](/guides/migration/success-to-positive/), and [link and button navigation](/guides/migration/link-and-button-navigation/).

Customizing the inside of a component used to mean a wrapper class and `:deep()` selectors reaching into internal class names that were never a public API.

Dialtone 10 adds components to core and updates the existing set. Component Playgrounds let you exercise the available props and slots.

The primitive triad section covers DtBox and DtText. Dialtone 10 adds six other components.

**DtFilterPill** is new to core, promoted from a product recipe and rebuilt. It extends DtButton and supports a dropdown mode, a popover with custom content containers, deferred selection, read-only, and a clear action.

**DtSegmentedControl** is new. It switches views within a section and behaves like a radio group; DtTabGroup is for navigating between sections. It shares its traveling indicator with Tabs.

**DtResizable** is new: resizable panel layouts with handles and initial sizes.

### Visual refresh

The visual refresh applies the new type scale and tokens to existing components. DtAvatar, DtButton, and DtTabGroup also received API and behavior updates.

**DtAvatar** was rebuilt with numeric sizes. A stable `seed` produces a deterministic color; `family` and `variant` provide explicit control when needed. Presence indicators use an SVG mask to cut space from the avatar instead of drawing a border around the indicator, and `deactivated` is a first-class state. The [avatar guide](/guides/migration/avatar-updates/) lists the prop changes; this migration is manual.

**DtButton** gained composability: `startIcon` and `endIcon` slots (logical, not left and right), leading and trailing slots, slot class props, and `href` rendering.

**DtTabGroup** was refreshed, given a traveling selection indicator, and brought in line with the WAI-ARIA Tabs pattern.

### More component updates

Smaller changes across the set: DtScroller gains `before`, `after`, and `empty` slots and scroll-end events. DtHovercard exposes show and hide controls, and with DtPopover supports an external anchor element; DtPopover adds a `boundary` prop and keeps nested overlays inside a `<dialog>` ancestor's top layer. DtComboboxMultiSelect forwards input-level keyboard events and stops shrinking as chips are added. DtInput handles IME composition correctly. The tooltip directive supports Shadow DOM. DtChip's `interactive` prop now defaults to `false`; see the [chip guide](/guides/migration/chip-interactive/). The scrollbar directive's `never` modifier was renamed `always` to match what it does; see the [scrollbar guide](/guides/migration/scrollbar-always/).

**Rich Text Editor** gained a `@tiptap/static-renderer` Markdown converter, phone-number linking, table styling, full-width tables, `preserveWhitespace`, `allowBackgroundColor`, and `allowLineHeight`. It also adds Shadow DOM support and fixes focus return, keyboard navigation near links, suggestion positioning, paste cleanup, and the bubble menu.

**Icons.** New: fax-inbound and fax-outbound, compass, circle and circle-dashed, filter-filled, agent-assist-color, and the density and line-spacing set. Updated: the hand icon, the star and sparkle icons aligned to the Dialpad brand star, and `dialbot` and `dialpad-analytics-ai` moved to the squircle shape. The icon package gains a `/vue` export.

**Localization.** Korean and Swedish are supported locales. An unsupported stored or browser locale now falls back to a supported locale during initialization.

## Under the hood

The engineering changes reduce CSS conflicts, make APIs easier to predict, and move more behavior onto platform primitives.

**Cascade layers.** Dialtone CSS lives in four layers: `dialtone.reset`, `dialtone.base`, `dialtone.components`, `dialtone.utilities`. Utilities beat components through layer order rather than `!important` or source order. Unlayered application CSS takes precedence over layered Dialtone CSS for normal declarations; `!important` reverses layer order. Read the [cascade layers guide](/guides/migration/css-cascade-layers/) before upgrading. A no-layers build is available for phased adoption.

[Visual: four stacked bands labeled reset, base, components, utilities, with "your application CSS" above them. Net new; a simple diagram.]

**Registered custom properties.** The variables behind the opacity utilities (`--bgo`, `--fco`, `--bco`) are declared with `@property { inherits: false }`, so setting an opacity utility on a parent no longer bleeds into every descendant.

**Softer specificity.** Selected component selectors use `:where()` so application overrides need less specificity.

**Native dialog.** DtModal renders a `<dialog>` element and can use the browser's top layer when opened as a modal dialog. Dialtone still applies `v-dt-focustrap` and handles Escape-to-close behavior. The DOM structure changed; the [native dialog guide](/guides/migration/modal-native-dialog/) explains what to check.

**Focus directives.** `v-dt-focusgroup` adds roving tabindex, arrow-key navigation, wrapping, last-focused memory, and disabled-item skipping to composite widgets. `v-dt-focustrap` keeps Tab focus within a container and restores focus when the trap closes. Both are available to components and product interfaces. Read the introductions to [focusgroup](/dialtone/whats-new/posts/2026-4-15.md) and [focustrap](/dialtone/whats-new/posts/2026-4-21.md).

**Recipes became UI Kits.** The product-specific composites (navigation, chat, call bar, forms, workflows) moved out of the core package into UI Kit packages owned alongside the products that use them: `@dialpad/navigationkit`, `@dialpad/chatkit`, `@dialpad/callbarkit`, `@dialpad/formkit`, `@dialpad/workflowkit`. The generic ones, FilterPill and ItemLayout, were promoted to core. The [recipes guide](/guides/migration/recipes-to-ui-kits/) maps old imports to new, and [UI Kits](/ui-kits/) documents what lives where.

**Vue 2 support ended.** Dialtone 10 is Vue 3 only. See the [Vue 2 removal guide](/guides/migration/vue2-removal/) if you have a lingering consumer.

## Accessibility, collected

Color-assistive themes for red-weak and green-weak vision (`prota-deuter`) and blue-weak vision (`trita`) are first-class theme values, as is high contrast. `v-dt-focusgroup` and `v-dt-focustrap` give components and product interfaces shared keyboard behavior. DtModal uses a native `<dialog>`, and DtTabGroup follows the WAI-ARIA Tabs pattern. Focus-ring tokens gained an outset variant and an inset default so rings remain visible inside `overflow: hidden` containers.

CI runs accessibility tests for relevant Dialtone Vue changes. Visual regression and bundle-size checks run on eligible pull requests under their path and label conditions.

## The docs are written for your coding assistant too

Coding assistants need the same API, token, and migration context as a person. Dialtone now publishes that context in formats they can read directly.

Published component, foundation, guide, token, utility, and UI Kit content has a raw Markdown counterpart generated at build time. Interactive elements are removed, and API and data tables become plain Markdown tables. Pages with a raw counterpart offer Copy Markdown, Copy Markdown link, and Open as Markdown controls. The site also publishes `llms.txt` and `llms-full.txt`. Callouts use GFM `> [!KIND]` syntax rather than custom HTML. Generated ESLint and Stylelint rule tables are checked for freshness in CI.

The [Dialtone MCP server](/guides/mcp-server/) gives Claude Code, Cursor, and other MCP-capable assistants search over bundled Dialtone data: components, tokens, CSS utilities, icons, and guide prose. Its index marks deprecated or discouraged patterns and includes their replacements. Project-scoped configuration lets a team share the same server setup.

The [Dialtone CLI](/guides/cli/) provides `dialtone search`, `dialtone component <name>`, `dialtone token`, `dialtone utility`, and `dialtone docs`, with JSON output for scripts. When the required packages are available, it resolves component, token, utility, and icon data from the Dialtone version installed in the project; documentation content remains bundled. `dialtone prompt <name>` produces compact component context for assistants without MCP support. The [VS Code extension](/guides/vscode-extension/) and language server provide editor integrations through their own data paths.

For contributors, `.claude` rules encode logical naming, numeric sizes, token usage, and Playground variant conventions. They load into the assistant's context when working on Dialtone.

If your team uses a compatible coding assistant, install the MCP server as a migration aid. It can surface indexed patterns and deprecations while you work; it is not required to run the migration.

## Migrating

The [migration guide](/guides/migration/) collects twenty changes in dependency order. Most include automation for statically detectable work; the guides separate those changes from the remaining manual review.

```bash
# What does my codebase still need?
npx dialtone-migrate --health-check --cwd ./src

# Preview everything
npx dialtone-migrate --all --dry-run --cwd ./src

# Run required migrations interactively
npx dialtone-migrate --cwd ./src

# Or run all required migrations noninteractively
npx dialtone-migrate --all --yes --cwd ./src

# Include the opt-in deprecation migrations
npx dialtone-migrate --all --include-opt-in --yes --cwd ./src

# Confirm what remains after tests, theme smoke tests, and design QA
npx dialtone-migrate --health-check --cwd ./src
```

## What to do next

**If you design.** Screens using changed tokens or refreshed components may shift. Use [Visual Changes for Designers](/guides/migration/visual-changes/) and the running documentation site to separate an intended refresh from a regression. Learn the primitive triad and spacing scale; they are the shared vocabulary for specifications and prototypes.

**If you build.** Run the health check, then work through the guides in order. Review layout mappings, cascade-layer adoption, nested mode regions, Avatar use, and interaction changes by hand. The MCP server is an optional aid if your team uses a compatible coding assistant.

**If you manage a product.** Plan design QA and interaction-regression checks for each migrated surface. Dialtone 10 is a system refresh rather than a product redesign, but some dimensions, text wrapping, and component behavior can change.

## What stays the same

Shared spacing stops keep their pixel values, while nine layout mappings move to the nearest new stop. Renamed border-radius utilities keep the same radius values. Checkbox, radio, and select drawings are unchanged, though their surrounding type and spacing can shift. Severity renames preserve their semantic mapping; any color difference comes from the refreshed ramps, not from changing `danger` to `critical` or `success` to `positive`.

Deprecated aliases remain only where their migration guides say they do. For example, legacy radius classes and `success*` CSS tokens still compile, while `setTheme()` no longer sets `data-dt-theme` by default. Treat each guide as the compatibility contract for that change.
