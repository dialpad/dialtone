## Overview

Dialtone 10, formerly known as Dialtone Next, ships in September 2026. Its visual refresh comes from deeper changes to composition, sizing, theming, and documentation. Understanding those connections will help designers and engineers distinguish intended differences from regressions and follow the migration guidance for their product areas.

## Three core design concepts

The **Primitive Triad**, **Layout and Spacing**, and the **Mode Directive** are the three most impactful design changes introduced in Dialtone 10. They improve how components are designed and implemented, how sizes are expressed, and how color mode is scoped.

### 1. The Primitive Triad

Clear division of responsibility.

- [DtBox](/components/box.md) defines what a container is: its surface, border, spacing, size, and position.
- [DtStack](/components/stack.md) defines how its children are arranged.
- [DtText](/components/text.md) applies the type variant, tone, strength, and text behavior.

<dt-box surface="moderate" border-width="100" border-color="subtle" border-radius="400" padding="300" min-block-size="300" class="d-my-300 d-d-flex d-ai-center d-jc-center">
  <dt-text as="p" align="center" variant="body-sm" tone="muted">[visual]</dt-text>
  <!-- [Visual: render the composed card beside labels showing DtBox as the container, DtStack as the arrangement, and DtText as the typography. Deck slide 32. Static or inline-demo candidate.] -->
</dt-box>

That intent previously required multiple css utility class combinations and manual composition. The primitive APIs make supported values discoverable and validate them during development. CSS Utilities remain available for cases the components do not cover.

Together, the three components create one composition vocabulary across design, code review, documentation, and coding-assistant guidance. A card can be described as a **box** containing a vertical **stack** of **text** instead of as a list of unrelated CSS decisions. The props also keep the token choices visible at the point of use, which makes later system changes easier to trace.

```vue
<dt-box
  padding="300"
  surface="primary"
  border-width="100"
  border-color="subtle"
  border-radius="400"
  shadow="card"
>
  <dt-stack gap="200">
    <dt-text as="h3" variant="headline-md">Card title</dt-text>
    <dt-text variant="body-sm">Card body content with supporting text.</dt-text>
  </dt-stack>
</dt-box>
```

> [!INFO] Migration guide
> The [flex-to-stack migration](/guides/migration/flex-to-stack/) covers existing flex utility groups and the cases that still need review.

### 2. Layout and Spacing

Two straight-forward design token dimension scales address different questions.

- **Spacing**: how much air an interface needs through padding, margin, gap, and inset. Its base is 8px.
- **Layout**: how big something is through width, height, and min/max dimensions. Its base is 64px.

<dt-box surface="moderate" border-width="100" border-color="subtle" border-radius="400" padding="300" min-block-size="300" class="d-my-300 d-d-flex d-ai-center d-jc-center">
  <dt-text as="p" align="center" variant="body-sm" tone="muted">[visual]</dt-text>
  <!-- [Visual: show 16px spacing and 128px layout expressed as a token, a utility class, and a DtBox prop, with 8 × 2 and 64 × 2. Deck slides 35 through 37. Static.] -->
</dt-box>

The previous `space` and `size` scales were ordinal: the suffix described a token's position in a list, not its value. A reader had to look up why one stop meant 16px and another meant 128px. The new names and bases make that distinction explicit.

The suffix is a multiplier rather than a position in an arbitrary list. `spacing-200` is 16px because 8 × 2; `layout-200` is 128px because 64 × 2. The same numbers run through design tokens, utility classes, and component props.

> [!INFO] Migration guide
> The [Layout and Spacing migration guide](/guides/migration/layout-and-spacing-tokens/) provides the complete scales, old-to-new mappings, tooling, and edge cases.

### 3. The Mode Directive

Some regions need a different color mode from their surroundings: a call bar, a hovercard over a light page, or a calling experience that stays dark. The [Mode Directive](/components/mode-island.md) scopes that decision to one element and everything inside it.

<dt-box surface="moderate" border-width="100" border-color="subtle" border-radius="400" padding="300" min-block-size="300" class="d-my-300 d-d-flex d-ai-center d-jc-center">
  <dt-text as="p" align="center" variant="body-sm" tone="muted">[visual]</dt-text>
  <!-- [Visual: show a call bar using invert, a dark hovercard over a light app, and an always-dark call panel beside light content. Deck slides 12 through 15. Static sequence or short muted video; sanitize product content.] -->
</dt-box>

These regions previously depended on component-specific inverted variants, inverted token choices, or local overrides. Moving mode to the containing element lets the components inside it use their normal semantic tokens and respond together.

```vue
<dt-box v-dt-mode:invert>...</dt-box>
<dt-box v-dt-mode:dark>...</dt-box>
<dt-box v-dt-mode:light>...</dt-box>
```

Modes can nest, and [DtModeIsland](/components/mode-island.md) provides the same behavior when a wrapper component is more practical than a directive.

> [!INFO] Migration guide
> The [theme-to-mode migration guide](/guides/migration/theme-to-mode/) covers deprecated theme calls, affected inverted variants, and the regions that need manual placement.

## Design Foundations

### Theming

Theme selection is now four independent dimensions.

1. **Brand** controls product-wrapper colors.
1. **Mode** controls light and dark appearance, including nested regions.
1. **Contrast** strengthens foregrounds and borders.
1. **Material** changes the neutral palette used by most foreground, surface, and border tokens.

<dt-box surface="moderate" border-width="100" border-color="subtle" border-radius="400" padding="300" min-block-size="300" class="d-my-300 d-d-flex d-ai-center d-jc-center">
  <dt-text as="p" align="center" variant="body-sm" tone="muted">[visual]</dt-text>
  <!-- [Visual: change brand, mode, contrast, and material through the Appearance panel. Deck slides 05 through 09. Short muted video or four stills; sanitize experimental names and internal content.] -->
</dt-box>

Separating those dimensions lets a product change one without encoding the others into the same theme name. The default Sandstone material, for example, warms the neutral ramp without changing the component API.

Brand remains deliberately narrow: it changes wrapper areas such as navigation without recoloring every content surface. Material carries the broader neutral tone. The base theme loads once, then `data-dt-*` attributes or runtime setters apply only the selected brand, mode, contrast, and material overrides.

> [!INFO] Migration Guide
> [Theme and Mode](/guides/theme-and-mode/) documents the current attributes and runtime APIs. Existing consumers should use the [theme-to-mode migration guide](/guides/migration/theme-to-mode/) for the API and attribute changes.

### Color

Every base color ramp now uses the same twelve stops from 50 through 1000. The number identifies the same relative position across each ramp, replacing the irregular stops that had accumulated as new shades were added. Semantic foreground, surface, and border tokens remain the intended product interface; the [Product Color Palette](/foundations/colors/palette/) documents the current set.

<dt-box surface="moderate" border-width="100" border-color="subtle" border-radius="400" padding="300" min-block-size="300" class="d-my-300 d-d-flex d-ai-center d-jc-center">
  <dt-text as="p" align="center" variant="body-sm" tone="muted">[visual]</dt-text>
  <!-- [Visual: compare the old irregular ramp stops with the normalized 50 through 1000 scale. Deck slides 16 through 20. Static pair or two-step reveal.] -->
</dt-box>

Each adjacent stop is visually distinct, and the shared numbering makes comparisons between hues more predictable. Product colors were retuned where needed, including blues that had drifted toward purple, while brand-specific hues changed less.

Colors are now defined in OKLCH instead of HSL or HEX. OKLCH gives Dialtone more predictable control over perceived lightness and chroma across different hues. Relative color syntax then applies opacity from a complete color token, removing the separate channel variables previously needed for each color.

Dialtone can now shape lightness, chroma, and hue independently while keeping the ramps structurally and perceptually consistent. This matters most in the middle and dark ends of a ramp, where equal HSL lightness steps under the previous system may not have produced equal-looking results across colors.

The rebuild removes over 3,200 custom-property declarations from the theme CSS, reducing its minified size by 33%.7%.

### Typography

The default body size moves from 15px to 16px, and the type scale expands from five sizes to eleven. Smaller intervals make it possible to adjust hierarchy without jumping two sizes, while the largest headline moves from 38px to 32px.

### Logical naming

Props, slots, utilities, and custom CSS now use start and end instead of assuming left and right. For example, `padding-left` becomes `padding-inline-start`, which follows the document's writing direction.

<dt-box surface="moderate" border-width="100" border-color="subtle" border-radius="400" padding="300" min-block-size="300" class="d-my-300 d-d-flex d-ai-center d-jc-center">

  <!-- [Visual: compare physical and logical names across props, utilities, and custom CSS. Deck slide 34. Static.] -->
</dt-box>

The same model applies to the block axis for top and bottom. Using CSS's inline and block vocabulary keeps component props, utility classes, and custom styles aligned.

> [!INFO] Migration Guide
> The [logical naming guide](/guides/migration/logical-naming/) covers the complete rename set. The [border-radius guide](/guides/migration/border-radius/) covers radius utilities that adopted logical names and numeric stops at the same time.

### Component APIs

Affected components now share a smaller vocabulary for common concepts. Four changes capture the direction:

| Before | Dialtone 10 |
| --- | --- |
| `size="md"` | `:size="300"` |
| `v-model:show` or `:show` | `v-model:open` or `:open` |
| `danger` or `success` | `critical` or `positive` |
| Styled anchors and router links | `<dt-button href>` and `<dt-link :to>` |

Numeric sizes align component APIs with the token scale. Open state, severity names, and navigation behavior no longer vary by component. Supported internal customization points also expose documented `*-class` props instead of requiring selectors that depend on private class names.

Positive boolean names follow the same rule: affected `hide*` props become `show*`, so enabling a feature no longer means setting a negative prop to false. Overlay labels and form events also move toward shared names where the affected components support them.

> [!INFO] Migration Guide
> The migration guides contain the full before-and-after inventory and tooling: [component props](/guides/migration/component-props/), [component sizes](/guides/migration/component-sizes/), [success to positive](/guides/migration/success-to-positive/), and [link and button navigation](/guides/migration/link-and-button-navigation/).

## Engineering foundations

### CSS architecture

Dialtone CSS now uses named cascade layers for reset, base, components, and utilities. Layer order makes utility precedence predictable while leaving unlayered application CSS in control during phased adoption. The [cascade layers guide](/guides/migration/css-cascade-layers/) explains the available builds and what application overrides need to consider.

<dt-box surface="moderate" border-width="100" border-color="subtle" border-radius="400" padding="300" min-block-size="300" class="d-my-300 d-d-flex d-ai-center d-jc-center">
  <dt-text as="p" align="center" variant="body-sm" tone="muted">[visual]</dt-text>
  <!-- [Visual: show reset, base, components, utilities, and unlayered application CSS in precedence order. Net-new static diagram.] -->
</dt-box>

Registered `@property` declarations stop opacity utilities from inheriting into descendants, and selected `:where()` selectors make component styles easier to override without adding specificity.

### Platform and packages

DtModal now renders a native `<dialog>` while retaining Dialtone's focus trapping and close behavior. Its DOM and top-layer behavior changed, so consumers that target internals should read the [native dialog guide](/guides/migration/modal-native-dialog/).

The [focusgroup](/dialtone/whats-new/posts/2026-4-15.md) and [focustrap](/dialtone/whats-new/posts/2026-4-21.md) directives make shared keyboard navigation and focus containment available to components and product interfaces. Product-specific recipes moved into distinct [UI Kits](/ui-kits/); the [recipes migration guide](/guides/migration/recipes-to-ui-kits/) maps the old imports. Dialtone 10 is Vue 3 only, with remaining Vue 2 consumers covered by the [Vue 2 removal guide](/guides/migration/vue2-removal/).

Reusable interaction behavior now relies more on browser primitives and shared directives, while product-specific composition lives with the teams that manage those interfaces.

### Accessibility

Color-assistive and high-contrast themes are first-class theme values. Shared focus directives, native dialog semantics, the WAI-ARIA Tabs pattern, and focus-ring tokens improve keyboard and visual access across the component set. These changes still depend on product context, so component pages and [Accessibility and inclusive design](/guides/accessibility/) remain the source for implementation guidance.

CI runs accessibility tests for relevant Dialtone Vue changes. Visual regression and bundle-size checks run on eligible pull requests under their path and label conditions.

## Migrating

### Start with the health check

The [migration guide](/guides/migration/) orders changes by dependency so later conversions build on earlier ones. Most statically detectable work has automation; each guide separates that work from its manual checks. Start with the health check:

```bash
npx dialtone-migrate --health-check --cwd ./src
```

Use the results to choose the relevant guides. Color, token, component, and framework migrations stay in a defined sequence because later tools expect earlier names and foundations to be in place.

### What remains manual

Tooling cannot choose application cascade-layer adoption, place Mode directives, review each Avatar use, complete a Vue 2 migration, or verify interaction changes. After automation, run component tests, interaction checks, theme smoke tests, and design QA. [Visual Changes for Designers](/guides/migration/visual-changes/) identifies intentional differences and the surfaces expected to remain unchanged.

Review representative product states rather than only default component examples. Include nested overlays, disabled and loading states, long or localized text, keyboard navigation, and each supported appearance combination.

### What stays the same

Semantic renames do not intentionally change meaning, and some deprecated aliases remain during migration. Visual differences should come from the refreshed foundations or documented component changes, not from a vocabulary rename alone. Treat each migration guide as the compatibility contract for its change.
