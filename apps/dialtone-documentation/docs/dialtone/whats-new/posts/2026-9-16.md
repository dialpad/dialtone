## Overview

Dialtone 10 brings visual refreshes to the Design Language, Design Tokens, and Components, alongside deeper changes to composition, layout/spacing system, theming, and documentation.

## Three core design concepts

The **Primitive Triad**, **Layout and Spacing**, and the **Mode Directive** are the three most impactful design changes being introduced. They improve how components are designed and implemented, how dimensions are expressed, and how color mode is scoped.

### 1. The Primitive Triad

A clear division of UI layout.

- [DtBox](/components/box.md) defines what a container is: its surface, border, spacing, size, and position.
- [DtStack](/components/stack.md) defines how its children are arranged.
- [DtText](/components/text.md) for typography variants, tone, strength, and text behavior.

<dt-box surface="moderate" border-width="100" border-color="subtle" border-radius="400" padding="300" min-block-size="300" class="d-my-300 d-d-flex d-ai-center d-jc-center">
  <dt-text as="p" align="center" variant="body-sm" tone="muted">[visual]</dt-text>
  <!-- [Visual: render the composed card beside labels showing DtBox as the container, DtStack as the arrangement, and DtText as the typography. Deck slide 32. Static or inline-demo candidate.] -->
</dt-box>

Previously that intent required multiple css utility class combinations. These primitive components improve their discoverability and validate them during development. CSS Utilities still remain available for cases the components do not cover.

Together, the three components are a cohesive and fast composition vocabulary across design, code review, documentation, and coding-assistant guidance. For example, a card may be described as a **Box** containing a vertical or horizontal **Stack** of **Text** elements instead of raw html paired with inline or custom CSS decisions. Those props keep the design choices visible at their point of use, additionally managing system changes easier to trace.

```vue demo
<dt-box
  padding="200"
  surface="primary"
  border-width="100"
  border-color="subtle"
  border-radius="400"
  shadow="card"
  inline-size="400"
>
  <dt-stack gap="50">
    <dt-text as="h3" variant="headline-md">Card title</dt-text>
    <dt-text as="p" variant="body-sm" max-lines="3">Card body content with supporting text. Lorem ipsum dolor sit amet, consectetur adipiscing elit.</dt-text>
  </dt-stack>
</dt-box>
```

### 2. Layout and Spacing

Two straight-forward design token dimension scales address different questions:

| Type | Decision | Base unit |
| -------- | -------- | -------- |
| Spacing | how much air an interface needs through padding, margin, gap, and inset. | 8px |
| Layout | how big something is through width, height, and min/max dimensions. | Cell |

<dt-box surface="moderate" border-width="100" border-color="subtle" border-radius="400" padding="300" min-block-size="300" class="d-my-300 d-d-flex d-ai-center d-jc-center">
  <dt-text as="p" align="center" variant="body-sm" tone="muted">[visual]</dt-text>
  <!-- [Visual: show 16px spacing and 128px layout expressed as a token, a utility class, and a DtBox prop, with 8 × 2 and 64 × 2. Deck slides 35 through 37. Static.] -->
</dt-box>

The previous `space` and `size` scales were ordinal: the suffix described a token's position in a list, with no real way to identify its value. One had to look up why one stop meant 16px and another meant 128px. The new names and bases make that distinction explicit.

The suffix is a multiplier rather than a position in an arbitrary list. `spacing-200` is 16px because 8 × 2; `layout-200` is 128px because 64 × 2. This convention is consistently used across design tokens (e.g. `--dt-spacing-200`), utility classes (e.g. `d-p-200`), and component props (e.g. `gap="200"`).

```css
.thing {
  padding: var(--dt-spacing-200); // 16px
  width: var(--dt-layout-200); // 128px
}
```

```html
<el class="d-p-200 d-w-200">
  <!--
    Same multiplier, different base scales:
    d-p-200: 2 × 8px = 16px
    d-w-200: 2 × 64px = 128px
  -->
</el>
```

> [!INFO] Migration guide
> The [Layout and Spacing migration guide](/guides/migration/layout-and-spacing-tokens/) provides the complete scales, old-to-new mappings, tooling, and edge cases.

### 3. The Mode Directive

Some UI regions often need a different mode from their surroundings. Current examples in the product include the call bar, an inverted hovercard, or a portions of a Dialpad Meeting. The [Mode Directive](/components/mode-island.md) scopes that decision to one element and everything inside it.

<dt-box surface="moderate" border-width="100" border-color="subtle" border-radius="400" padding="300" min-block-size="300" class="d-my-300 d-d-flex d-ai-center d-jc-center">
  <dt-text as="p" align="center" variant="body-sm" tone="muted">[visual]</dt-text>
  <!-- [Visual: show a call bar using invert, a dark hovercard over a light app, and an always-dark call panel beside light content. Deck slides 12 through 15. Static sequence or short muted video; sanitize product content.] -->
</dt-box>

Previously these implementations often depended on custom local styles to invert color design tokens. Moving mode to the containing element allows elements within to use their normal semantic tokens and render accordingly.

```vue
<dt-box v-dt-mode:invert>
  <!-- Opposite mode of parent -->
</dt-box>
<dt-box v-dt-mode:dark>
  <!-- always dark -->
</dt-box>
<dt-box v-dt-mode:light>
  <!-- always light -->
</dt-box>
```

## Design Foundations

### Theming

Theming now now a layered system via four independent dimensions.

1. **Brand** controls product-wrapper colors.
1. **Mode** light or dark appearance.
1. **Contrast** strengthens foreground and borders.
1. **Material** changes the neutral palette used by most foreground, surface, and border design tokens.

<dt-box surface="moderate" border-width="100" border-color="subtle" border-radius="400" padding="300" min-block-size="300" class="d-my-300 d-d-flex d-ai-center d-jc-center">
  <dt-text as="p" align="center" variant="body-sm" tone="muted">[visual]</dt-text>
  <!-- [Visual: change brand, mode, contrast, and material through the Appearance panel. Deck slides 05 through 09. Short muted video or four stills; sanitize experimental names and internal content.] -->
</dt-box>

This layered dimension approach allows changing one without encoding the others into the same theme name.

The use case for the Brand dimension remains deliberately narrow: it changes the wrapper areas such as navigation without recoloring every content surface. The base brand theme loads once, then `data-dt-*` attributes or runtime setters apply only the selected brand, mode, contrast, and material as overrides.

> [!INFO] Migration Guide
> [Theme and Mode](/guides/theme-and-mode/) documents the current attributes and runtime APIs. Existing consumers should use the [theme-to-mode migration guide](/guides/migration/theme-to-mode/) for the API and attribute changes.

### Color

Every base color ramp (eg. red, purple, black, etc.) now uses the same twelve stops from 50 through 1000, replacing the irregular stops that had accumulated over time (e.g. 550). Semantic foreground, surface, and border tokens remain the intended product interface; the [Product Color Palette](/foundations/colors/palette/) documents the current set.

<dt-box surface="moderate" border-width="100" border-color="subtle" border-radius="400" padding="300" min-block-size="300" class="d-my-300 d-d-flex d-ai-center d-jc-center">
  <dt-text as="p" align="center" variant="body-sm" tone="muted">[visual]</dt-text>
  <!-- [Visual: compare the old irregular ramp stops with the normalized 50 through 1000 scale. Deck slides 16 through 20. Static pair or two-step reveal.] -->
</dt-box>

All colors are now defined using [OKLCH](https://evilmartians.com/chronicles/oklch-in-css-why-quit-rgb-hsl) rather than HSL. OKLCH gives Dialtone more predictable control over perceived lightness and chroma across different hues. Relative color syntax then applies opacity from a complete color token, removing the separate channel variables previously needed for each color.

Dialtone can now shape lightness, chroma, and hue independently while keeping the ramps structurally and perceptually consistent. This matters most in the middle and dark ends of a ramp, where equal HSL lightness steps under the previous system may not have produced equal-looking results across colors.

Refactoring to OKLCH allowed for the removal of over 3,200 custom property declarations CSS, and reduced the Dialtone build size by a third.

### Typography

The default body size moves from 15px to 16px, and textscale doubled for more granularity. Smaller intervals make it possible to adjust hierarchy when needed.

Body text appears throughout the product, so the default-size change is one of the release's most visible effects. DtText does not expose every raw size as a semantic variant; pair `size` with a variant when an exception needs one.

A new component, [DtText](/components/text.md), provides a straightforward way to render text in semantic and styled variants via props for product typography. It is the recommended way to apply styled text.

### Refreshed

The new color, type, and spacing foundations intentionally change parts of the component library. [Visual Changes for Designers](/guides/migration/visual-changes/) documents full before-and-after inventory and explains how to distinguish an intended refresh from a migration regression.

#### [DtAvatar](/components/avatar.md)

DtAvatar now uses numeric sizes, deterministic theme-aware colors, clearer deactivated styling, and presence indicators that cut space from the avatar. Its migration is manual; use the [Avatar migration guide](/guides/migration/avatar-updates/) for the required review.

#### [DtButton](/components/button.md)

DtButton adds logical icon slots, leading and trailing content, supported slot class props, and native navigation through `href` or `to`.

#### [DtTabGroup](/components/tabs.md)

Scroller, overlays, form controls, Rich Text Editor, icons, and localization also received smaller API, behavior, accessibility, or content updates. Two changes require direct action: DtChip now requires `interactive="true"` when a chip should respond to click or keyboard input, and the scrollbar directive's `never` modifier is now named `always`. Use the [Chip migration guide](/guides/migration/chip-interactive/) and [Scrollbar migration guide](/guides/migration/scrollbar-always/) for those changes. Rich Text Editor, icon, and locale additions are summarized in the release notes rather than repeated here.

## Engineering foundations

### CSS architecture

Dialtone CSS now uses named cascade layers for reset, base, components, and utilities. Layer order makes utility precedence predictable while leaving unlayered application CSS in control during phased adoption. The [cascade layers guide](/guides/migration/css-cascade-layers/) explains the available builds and what application overrides need to consider.

Registered `@property` declarations stop opacity utilities from inheriting into descendants, and selected `:where()` selectors make component styles easier to override without adding specificity.

### Platform and packages

DtModal now renders a native `<dialog>` while retaining Dialtone's focus trapping and close behavior. Its DOM and top-layer behavior changed, so consumers that target internals should read the [native dialog guide](/guides/migration/modal-native-dialog/).

The [focusgroup](/dialtone/whats-new/posts/2026-4-15.md) and [focustrap](/dialtone/whats-new/posts/2026-4-21.md) directives make shared keyboard navigation and focus containment available to components and product interfaces. Product-specific recipes moved into distinct [UI Kits](/ui-kits/); the [recipes migration guide](/guides/migration/recipes-to-ui-kits/) maps the old imports. Dialtone 10 is Vue 3 only, with remaining Vue 2 consumers covered by the [Vue 2 removal guide](/guides/migration/vue2-removal/).

Reusable interaction behavior now relies more on browser primitives and shared directives, while product-specific composition lives with the teams that manage those interfaces.

### Component APIs

Affected components now share a smaller vocabulary for common concepts. Most can be categorized by four key changes:

| Before | Dialtone 10 |
| --- | --- |
| `size="md"` | `:size="300"` |
| `v-model:show` or `:show` | `v-model:open` or `:open` |
| `danger` or `success` | `critical` or `positive` |
| Styled anchors and router links | `<dt-button href>` and `<dt-link :to>` |

Numeric sizes align component APIs with the token scale. Open state, severity names, and navigation behavior no longer vary by component. Supported internal customization points also expose documented `*-class` props instead of requiring selectors that depend on private class names.

Positive boolean names follow the same rule: affected `hide*` props become `show*`, so enabling a feature no longer means setting a negative prop to false. Overlay labels and form events also move toward shared names where the affected components support them.

> [!INFO] Migration Guide
> The migration guides contain the full before-and-after inventory and tooling: [component props](/guides/migration/component-props/), [component sizes](/guides/migration/component-sizes/), [success to positive](/guides/migration/success-to-positive/), and [link and button navigation](/guides/migration/link-and-button-navigation/).

### Accessibility

Color-assistive and high-contrast themes are first-class theme values. Shared focus directives, native dialog semantics, the WAI-ARIA Tabs pattern, and focus-ring tokens improve keyboard and visual access across the component set. These changes still depend on product context, so component pages and [Accessibility and inclusive design](/guides/accessibility/) remain the source for implementation guidance.

CI runs accessibility tests for relevant Dialtone Vue changes. Visual regression and bundle-size checks run on eligible pull requests under their path and label conditions.

## Migrating

### Start with the health check

The [migration guide](/guides/migration/) orders changes by dependency so later conversions build on earlier ones. Most statically detectable work has automation; each guide separates that work from its manual checks. Start with the health check:

```bash
npx dialtone-migrate --health-check --cwd ./src
```

Use the results to choose the relevant guides. Color, token, component, and framework migrations stay in a defined sequence because later tools expect earlier names and foundations to be in place.

### What remains manual

Tooling cannot choose application cascade-layer adoption, place Mode directives, review each Avatar use, complete a Vue 2 migration, or verify interaction changes. After automation, run component tests, interaction checks, theme smoke tests, and design QA. [Visual Changes for Designers](/guides/migration/visual-changes/) identifies intentional differences and the surfaces expected to remain unchanged.

Review representative product states rather than only default component examples. Include nested overlays, disabled and loading states, long or localized text, keyboard navigation, and each supported appearance combination.

### What stays the same

Semantic renames do not intentionally change meaning, and some deprecated aliases remain during migration. Visual differences should come from the refreshed foundations or documented component changes, not from a vocabulary rename alone. Treat each migration guide as the compatibility contract for its change.
