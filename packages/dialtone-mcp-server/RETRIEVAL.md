# MCP retrieval contract

Tool replies use C2 schema version 1 in `structuredContent` and a text fallback containing the same JSON facts. The adapter version is reported in MCP initialization; each result separately identifies its data packages and versions.

Token and utility discovery use `projection: "summary"` by default. Each item retains its source name/type and complete migration metadata, shows up to two `previewValues`, and reports `valueCounts` with total, previewed and omitted records. Token previews name their source theme; they do not identify the active theme. Omitted values are explicitly reported, and each item supplies an exact detail call.

Use `search_tokens` with `{ "query": "--dt-color-foreground-primary", "projection": "themes" }` for complete named theme records. Use `search_utility_classes` with `{ "query": "d-chip__close", "projection": "properties" }` for complete property records. These projections require an exact source name, return `mode: "detail"`, retain all available migration metadata, and apply existing limit/offset pagination to intact theme/property records. Broad phrases and unknown names return `no-match` with a summary-discovery route. They share the 12000-token detail budget; a single oversized contract is still explicitly unavailable.

Use `search_components` to discover candidates, then `get_component` with a canonical name or unique alias. A selected component constrains field lookup: `{ "component": "DtButton", "projection": "props", "field": "kind" }` returns the complete available property record, including values, defaults and deprecation tags. Projections are `all` (default), `props`, `events`, `slots`, `methods` and `expose`. Missing metadata remains unknown. Import hints retain their source-export verification; they do not prove installed compatibility or runtime imports.

Use `search_documentation` to discover section IDs, then `get_documentation` with an exact ID. For example, `{ "id": "components/checkbox#accessibility" }` retrieves the available accessibility prose, including guidance beyond discovery excerpts. Follow its `textOffset` continuation for remaining text. Text offsets count Unicode code points. This corpus contains prose; example code requires separate verification.

Every envelope reports `match` (`exact`, `candidate`, `no-match`, `unavailable` or `unverified`), canonical identity where selected, source, total/returned record counts, omissions and a precise continuation call. Discovery omits component API detail, descriptions after 280 characters, and documentation prose after 500 characters. Component API detail pages retain intact generated records; allowed values, payloads and scoped bindings are never silently sliced.

Queries, component names, field names and section IDs are trimmed nonempty strings of at most 256 characters. Integer limits are 1–50 for CSS utilities, tokens, icons and component detail, and 1–30 for component/documentation discovery. Defaults are 15 for utilities/tokens, 20 for icons/detail and 10 for component/documentation discovery. Record offsets default to zero and range from 0 to 100000. `get_documentation` defaults to 6000 code points per text page, accepts 1–10000, and accepts text offsets from 0 to 1000000. Invalid types, whitespace, zero/negative/fractional limits, out-of-range values and unknown arguments return an error envelope.

Discovery has a budget of 1500 estimated tokens; detail has 12000. The rough counting method is `ceil(UTF-8 bytes of compact envelope JSON / 4)`, not a model tokenizer or measured token saving. Both representations contain the same envelope. Pagination stops between intact records; an atomic record that exceeds its budget reports `unavailable` and `atomic_contract_exceeds_budget`. Request a narrower projection or named field when the component view is too large. No continuation is emitted if it cannot make progress.

Sources are bundled and `installedCompatibility` is `not_checked`. Each domain reports package/version/schema, `hash` (SHA256 of exact artifact bytes) and `contentHash` (SHA256 of canonically ordered JSON with only the declared build repository prefix removed from `sourceFiles`, retaining semantic directories). `buildHash` combines domain content identities and package/schema versions deterministically. Raw artifact hashes can differ across checkout paths; normalized content identity remains stable when declared repository prefixes alone differ. No timestamp or absolute build path is added to these stamps. Hash equality identifies data; it does not prove factual correctness or availability in a consumer project.

Documentation links are generated from authored component API references and literal companions, joined through C1 public identities and routed by VuePress. They identify latest production references, with readiness and API-content verification stated separately. Missing associations have no invented URL; conflicting associations have no asserted primary URL. Migration advice remains separate from a component’s own documentation page. Deployed page availability and API completeness require separate verification.

Initialization instructions cover tool routing within 100 words, with the essential discover/select/detail/continue/source route in the first 512 characters. The existing `dialtone://client-rules` resource remains available.
