Lint for `AGENTS.md` and `.agents/**`: ESLint covers `.js`, `.mjs` and `.cjs`; markdownlint and prettier cover `.md`. Markdown is compared with its copy at `$BASE` and fails only on new findings (the rest of `.agents/` already has findings on `staging`). ESLint fails on errors only; existing warnings are notes.

```sh
: "${BASE:?set BASE to the recorded base SHA}"
CHANGED=$({ git diff --name-only --diff-filter=d "$BASE" -- AGENTS.md .agents; git ls-files -o --exclude-standard -- AGENTS.md .agents; })
echo "$CHANGED" | grep -E '\.(js|mjs|cjs)$' | xargs pnpm exec eslint
echo "$CHANGED" | grep -E '\.md$' | while read -r f; do
  now=$(pnpm exec prettier --check --single-quote "$f" >/dev/null 2>&1; echo $?)
  was=$(git show "$BASE:$f" 2>/dev/null | pnpm exec prettier --check --single-quote --stdin-filepath "$f" >/dev/null 2>&1; echo $?)
  [ "$now" != 0 ] && [ "$was" = 0 ] && echo "new prettier failure: $f"
  now=$(pnpm exec markdownlint "$f" 2>&1 | wc -l)
  was=$(git show "$BASE:$f" 2>/dev/null | pnpm exec markdownlint --stdin 2>&1 | wc -l)
  [ "$now" -gt "$was" ] && echo "new markdownlint findings: $f"
done
```

No output from the markdown loop and no ESLint errors means pass. Findings that already exist at `$BASE` are a note, not a failed gate.

Notes:

- A lint finding in a file the diff does not touch is a note, not a failed gate.
- A test that fails in a file the diff does not touch and fails the same way at `$BASE` is pre-existing: name it as a note, not a failed gate. (On `staging` today, three codemod tests fail this way: two ESLint-rule map checks in `dialtone_migrate_border_radius` and one `hsl-to-oklch` test.)
- When `dialtone-tokens` or `dialtone-css` changes a public token or class, also run the `dialtone-vue` test gate as a downstream check.
- A package not in the table: read its `package.json` scripts and run its `lint` and `test` if present. Skip any script that writes files (`--fix`); run the underlying checker without it.
- If the dependency install is missing or fails, say so and mark the gates "not run". Do not work around a failed install.
- Builds, `build-storybook` and visual tests are CI's job. Run a build only when a changed public export, token or icon needs it to prove a downstream package still compiles, and say why.
- `.agents/resources/validation.md` lists the wider checks (builds, acceptance scenarios) for areas outside this table.
