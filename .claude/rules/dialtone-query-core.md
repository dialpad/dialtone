# Dialtone Query Core Rules

The shared search engine behind `dialtone-mcp-server`, `dialtone-cli`, and (eventually) the language server. All search logic, types, data loading, and result formatting live here — transports stay thin.

## Architecture

```text
dialtone-query-core (search engine)
├── dialtone-mcp-server (MCP transport)
├── dialtone-cli (terminal interface)
└── language-server (LSP integration)
```

Transports must NOT contain search logic. New search behavior, ranking changes, or result formatting belongs in this package.

## File Layout

```text
packages/dialtone-query-core/
├── src/
│   ├── index.ts       # Public API barrel — only exports listed here are public
│   ├── types.ts       # All TypeScript interfaces
│   ├── data.ts        # JSON imports from workspace deps
│   ├── tools/         # search + format functions per domain
│   │   ├── components.ts
│   │   ├── utility-classes.ts
│   │   ├── tokens.ts
│   │   ├── icons.ts
│   │   └── docs.ts
│   └── utils/         # shared helpers (filters, etc.)
└── tests/tools/       # Vitest specs with in-memory fixtures
```

## Module System

ESM only (`"type": "module"` in `package.json`).

- TypeScript imports MUST use the `.js` extension despite the source being `.ts`:
  ```typescript
  import type { SearchResult } from '../types.js';     // ✅
  import { applySmartFilter } from '../utils/filters.js'; // ✅
  import type { SearchResult } from '../types';        // ❌ breaks ESM output
  ```
- Use `export type { ... }` for type-only exports — keeps the runtime barrel free of type erasure ceremony.

## Public API Surface

`src/index.ts` is the ONLY public entry point. Helper functions inside tool files (e.g., `splitCamelCase`, `removeDuplicates`, `searchByName`) stay private — do not export them.

When adding a new search tool:
1. Implement it in `src/tools/<domain>.ts`.
2. Add the type definitions to `src/types.ts`.
3. Re-export the public surface in `src/index.ts`.

## Data Loading

Production data comes from sibling workspace dependencies — never duplicate JSON here.

```typescript
import utilityClassesData from '@dialpad/dialtone-css/lib/dist/dialtone-docs.json' with { type: 'json' };
import componentsData from '@dialpad/dialtone-vue/component-documentation.json' with { type: 'json' };
import documentationData from '@dialpad/dialtone-docs/dist/public-docs.json' with { type: 'json' };
```

- Use the `with { type: 'json' }` import attribute — NOT the deprecated `assert { type: 'json' }` syntax.
- Cast with `as unknown as <Type>` because TS cannot infer JSON shapes through workspace boundaries.
- `src/data.ts` is hand-written; the JSON files it imports are generated by their owning packages.

Downstream impact: changes to `data.ts` (new source, renamed field, schema change) ripple to `dialtone-mcp-server`, `dialtone-cli`, and the language server. Coordinate the bump.

## Tool Function Convention

Each domain in `src/tools/` exposes two functions:

```typescript
export function search<Domain>(
  query: string,
  data: <DomainData>
): { results: SearchResult[]; notes: string[] };

export function format<Domain>Results(
  results: SearchResult[],
  query: string
): string;
```

- `search*` does the matching, ranking, and filtering — returns structured results.
- `format*Results` returns a Markdown-formatted string for transport consumers to print directly.

## SearchResult Shape

All search functions return `SearchResult[]` with this shape:

```typescript
interface SearchResult {
  type: string;       // 'component' | 'utility-class' | 'design-token' | 'icon' | 'documentation'
  name: string;
  details: any;       // domain-specific payload
  metadata: Metadata | null;
  tier?: number;      // optional ranking tier (lower = higher priority)
}
```

New search domains MUST conform to this shape so unified results (`sortUnifiedResults`, `formatUnifiedResults`) work without special-casing.

## Deprecation & Discouragement

All deprecation/discouragement signals route through the shared `Metadata` interface:

```typescript
interface Metadata {
  deprecated?: boolean;
  discouraged?: boolean;
  category?: string;
  reason?: string;
  alternatives?: string[];
  docs?: string;
  replacement?: string;
}
```

Use `applySmartFilter` (from `src/utils/filters.ts`) to apply consistent deprecation/replacement behavior. Do NOT add ad-hoc deprecation flags to result `details` — extend `Metadata` if a new signal is needed.

## Logging Discipline

**stdout is reserved for tool output. Debug logging goes to stderr.**

```typescript
console.error(`[DEBUG] query: "${query}"`);     // ✅ debug
console.error(`[DEBUG] results: ${count}`);     // ✅ debug
console.log(`[DEBUG] ...`);                     // ❌ corrupts MCP/CLI output
```

MCP servers communicate over stdout — any stray `console.log` will break the JSON-RPC frame. The CLI also pipes stdout into format consumers. `console.error` is the only safe debug channel.

## Test Patterns

- Vitest only (`describe`, `test`, `expect`). No other frameworks.
- Tests use **in-memory fixtures**, never the production JSON files — keeps tests fast, deterministic, and isolated from data churn:
  ```typescript
  const fixture: DocumentationRecord[] = [
    { id: 'button#usage', docId: 'button', /* ... */ },
    // small, focused records that exercise the behavior under test
  ];
  ```
- Test files live under `tests/<area>/<file>.test.ts` mirroring `src/<area>/<file>.ts`.
- Run: `pnpm nx run dialtone-query-core:test` or `pnpm nx run dialtone-query-core:test --watch`.

## Build

- `pnpm nx run dialtone-query-core:build` — runs `tsc` against `tsconfig.json`.
- Outputs to `build/` (declared in `package.json` `files`, `main`, `types`).
- Rebuild before testing changes downstream: `pnpm nx run dialtone-query-core:build && pnpm nx run dialtone-mcp-server:build`.

## Anti-Patterns

- Putting search logic in `dialtone-mcp-server` or `dialtone-cli` — both must be thin transports over this package.
- Hardcoding fixture data in production code paths — fixtures belong in `tests/`.
- Importing from a workspace package's source directly (`@dialpad/dialtone-css/src/...`) — always go through the generated JSON.
- Adding deprecation fields outside the `Metadata` interface — extend the type, don't sidestep it.
- `console.log` anywhere in `src/` — breaks MCP transport.
- Omitting `.js` extensions in TS imports — breaks ESM build output.
- Exporting helper functions from tool files just to test them — refactor or test through the public surface.
